# 武器配件系统：塔科夫式改造规划

> 状态：**首版已实现**。旧的"四选一"配件系统仍隐藏（`ATTACHMENTS_ENABLED = false`），
> 新系统在 `shared/src/weapon-build.ts`：sight / muzzle / magazine / stock 四槽，
> 兼容性、有效属性、协议 build 段、服务端重算与军械库 3D 工作台已落地。
> 局内拾取/仓库/耐久仍按第 5 节留到后续阶段。

---

## 0. 为什么重做

现在的配件是"出击前四选一"：2× 镜 / 消音器 / 加长弹仓 / 加固枪托。每件直接
乘一个全局系数，没有接口、没有位置、没有重量，也没有来源与丢失。它回答的是
"这局带哪个 buff"，而不是"我这把枪是怎么改的"。

塔科夫式的核心不是"更多槽位"，而是三件事：

1. **枪是一个平台**：配件装在具体接口上，接口决定兼容性；
2. **改枪是取舍**：每件配件都同时给好处和代价（人机、重量、开镜速度、声音、
   价格、耐久），不存在纯上位；
3. **配件是身外之物**：能在局内找到、带出去、死掉时丢掉 —— 它必须接进
   "搜打撤"循环，否则只是另一张天赋卡。

## 1. 设计目标与不可违反的约束

| # | 约束 | 理由 |
|---|---|---|
| 1 | **服务端权威** | 射速、换弹、扩散、声音、弹匣容量必须由服务端按同一份纯函数算；客户端只做预测与表现。 |
| 2 | **纯函数组合** | `build + baseStats → effectiveStats` 必须是 shared 里的纯函数，两端共用。否则"客户端以为能开火、服务端拒绝"会再次出现。 |
| 3 | **兼容性先于数值** | 没有对应接口就不能装。兼容性用 mount tag 表达，不用武器 id 白名单。 |
| 4 | **没有纯上位** | 每件配件至少有一个维度是负收益，且价格/稀有度不能替代取舍。 |
| 5 | **协议不膨胀** | 快照 20Hz 不携带完整配件列表；配件只在低频包（配装/外观/战利品）里传。 |
| 6 | **重连不丢配装** | 配件属于角色状态，断线重连后原样恢复（与 `resumePlayer` 的其它状态一起）。 |
| 7 | **可回退** | 每个阶段都能独立上线；旧 `attachment` 字段与存档键保留到新系统稳定。 |

## 2. 槽位模型（首版）

武器分四类：杠杆步枪（1 / 4 / 6）、双管霰弹（2 / 3）、转轮（5）、刀（10）。
首版只做**三个槽**，先把"接口 → 兼容 → 数值 → 网络 → UI"整条链路跑通：

| 槽位 | 接口（mount tag） | 步枪 | 霰弹 | 转轮 | 刀 |
|---|---|---|---|---|---|
| `sight` 瞄具 | `dovetail` / `receiver-rail` | ✓ | ✓ | ✓（照门槽） | — |
| `muzzle` 枪口 | `thread` / `tube-band` | ✓ | ✓ | — | — |
| `magazine` 供弹 | `tube` / `cylinder` | ✓ | — | ✓ | — |

后续再开：

| 槽位 | 内容 | 为什么放后面 |
|---|---|---|
| `stock` 枪托/握把 | 加固托、轻量托、直托 | 与视图模型的后坐/摆动耦合最深，先不动动画。 |
| `action` 机件 | 调校击发、快装杠杆 | 改的是射速/换弹节奏，平衡风险最高。 |
| `ammo` 弹药 | 软尖/穿甲/鹿弹 | 它是独立系统（伤害/穿透/初速），不该塞进配件。 |

## 3. 数据模型

```ts
// shared/src/weapon-build.ts（新文件，纯数据 + 纯函数）

export type SlotKey = 'sight' | 'muzzle' | 'magazine' | 'stock' | 'action'

/** 接口标签：武器声明自己有什么，配件声明自己要什么。 */
export type MountTag =
  | 'dovetail'
  | 'receiver-rail'
  | 'thread'
  | 'tube-band'
  | 'tube'
  | 'cylinder'
  | 'stock-screw'

export interface AttachmentDef {
  id: number
  key: string
  name: string
  slot: SlotKey
  /** 需要的接口；武器必须全部满足。 */
  mounts: MountTag[]
  /** 同槽/跨槽互斥（例如长弹仓与短护木不可同时装）。 */
  conflicts?: string[]
  /** 对有效属性的修正。加法项与乘法项分开，见第 4 节。 */
  stats: Partial<WeaponStats>
  weightKg: number
  /** 视觉挂点 + 模型 key（weapon-models 里的 mount 名）。 */
  modelKey: string
  rarity: 0 | 1 | 2 | 3
  /** 商人价格；0 = 初始拥有。 */
  cost: number
  desc: string
}

export interface WeaponBuild {
  weaponId: number
  /** 槽位 → 配件 defId（0 = 空）。 */
  slots: Partial<Record<SlotKey, number>>
}

export interface WeaponStats {
  adsTimeScale: number       // 开镜时间乘数
  adsZoom: number            // 倍率（1 = 机瞄）
  recoilScale: number        // 视觉/弹道后坐乘数
  spreadScale: number        // 散布乘数
  reloadScale: number        // 换弹时间乘数
  cycleScale: number         // 射速间隔乘数
  loudnessScale: number      // 枪声传播乘数
  muzzleFlashScale: number   // 枪口火光乘数
  magazineBonus: number      // 弹匣/弹仓容量加成（加法）
  velocityScale: number      // 初速乘数（影响下坠与穿透）
  ergonomics: number         // 0..100，驱动摆动/切枪/开镜手感
  weightKg: number           // 总重（加法）
}
```

武器侧只需要在 `WEAPONS` 里补一个接口表，例如：

```ts
rifle.mounts = { sight: ['dovetail'], muzzle: ['thread', 'tube-band'], magazine: ['tube'] }
shotgun.mounts = { sight: ['dovetail'], muzzle: ['tube-band'] }
revolver.mounts = { sight: ['dovetail'], magazine: ['cylinder'] }
```

**为什么用 tag 而不是 `weaponIds: [1,4,6]`**：新增一把枪时只声明接口，所有已有
配件自动获得正确的兼容性判断；反过来每加一件配件都要回头改一堆武器表。

## 4. 数值组合与平衡

### 4.1 计算顺序

```ts
effective = base
  // 1) 加法属性（弹匣容量、重量）
  + additive(stats)
  // 2) 乘法属性逐个相乘
  * product(multiplier(stats))
  // 3) 夹到硬上限
  clamp(effective, caps)
```

乘数全部用"相对倍率"（1 = 不变），不要用"百分比加成"再转一次，避免 +20% 与
×0.8 混用后出现 1.0 这种反直觉结果。

### 4.2 硬上限（防止叠成怪物）

| 属性 | 下限 | 上限 | 备注 |
|---|---:|---:|---|
| `recoilScale` | 0.55 | 1.35 | 再低就是激光枪，再高不可用。 |
| `loudnessScale` | 0.25 | 1.4 | 消音器不能完全无声。 |
| `adsTimeScale` | 0.7 | 1.8 | 开镜慢于 1.8 倍等于残废，快于 0.7 等于瞬镜。 |
| `reloadScale` | 0.65 | 1.6 | 与弹匣容量一起形成"容量 vs 换弹"的取舍。 |
| `magazineBonus` | 0 | +4 | 首版最多 +4 发。 |
| `weightKg` | 0 | — | 总重进入 `ergonomics` 的线性惩罚。 |

### 4.3 取舍模板

每件配件按下面的模板写描述与数值，保证"没有纯上位"：

- **2× 镜**：`adsZoom 2.0`，但 `adsTimeScale 1.25`、`ergonomics -12`；
- **消音器**：`loudnessScale 0.45`、`muzzleFlashScale 0.2`，但
  `weight +0.35kg`、`adsTimeScale 1.12`、`velocityScale 0.96`；
- **加长弹仓**：`magazineBonus +2`，但 `reloadScale 1.15`、`weight +0.2kg`；
- **轻量枪托**：`ergonomics +10`、`adsTimeScale 0.92`，但 `recoilScale 1.15`；
- **加固枪托**：`recoilScale 0.82`，但 `ergonomics -8`、`weight +0.3kg`。

### 4.4 人机（ergonomics）

首版不要把它做成一个"看不见的数值"：它至少要驱动三件事，玩家能感觉到：

1. 开镜时间（`adsTimeScale` 再乘人机曲线）；
2. 切枪时间（`switchMs` 乘人机曲线）；
3. 视图模型的呼吸摆动幅度（腰射时）。

## 5. 经济与"搜打撤"

### 5.1 两条来源

- **商人购买**：金币一次性解锁，**永久拥有**（沿用现在的局外经济）。
- **局内拾取**：稀有配件作为战利品出现在搜刮点/补给空投/尸体上，
  **只在本局有效**，撤离后进入仓库（第二阶段），死亡则掉回尸体缓存。

### 5.2 与现有经济架构的冲突（必须先决策）

现在的金币、天赋解锁、配装全部存在 `localStorage`，服务端只收一个配装包。
塔科夫式"带出去 / 死掉丢失"要求**服务端知道玩家拥有什么**，否则客户端改
localStorage 就能刷满仓库。因此：

- **首版（无仓库）**：所有配件都用金币永久解锁，等价于现在的 2× 镜/消音器；
  不做局内拾取。这样只需要把"选择"从四选一改成多槽位，不碰后端。
- **第二阶段（局内掉落）**：配件实例由服务端在局内生成、记录、结算；撤离时
  只在结算包里告诉客户端"带出了哪些 defId"，客户端自己存仓库（仍可被改，
  但不影响对局内已有的公平性）。
- **第三阶段（真仓库）**：需要账号体系与服务端存档；这是另一个项目级的改造，
  不要和配件系统绑在一起上线。

### 5.3 死亡掉落

沿用现有 `BodyCache`：死亡时把已装配件的 defId 列表写进尸体缓存；搜尸者可以
拿走。首版只记录、不真正装配（因为首版配件是永久解锁），第二阶段再变成实物。

## 6. 界面与交互

### 6.1 出击页

- 主武器卡下方新增「改 枪」按钮，打开工作台覆盖层（复用 `overlay.ts` 的层）。
- 工作台左侧是武器轮廓 + 槽位热点；右侧是当前槽位的兼容列表。
- 每件配件显示：名称、稀有度、重量、价格、**属性变化预览**（装上前/后对比）。
- 不兼容项置灰并给出原因（缺接口 / 与某件冲突），不要直接隐藏 —— 玩家需要
  知道"为什么不能装"。
- 底部是两个按钮：「装配」「恢复原厂」。

### 6.2 局内

- 不在 HUD 常驻配件列表；信息通过行为体现（更小的枪声、更慢的开镜）。
- 地图覆盖层（M）显示当前武器名 + 关键配件缩略（可选）。

### 6.3 预设

第二阶段加入「保存配装」：一个武器可存 2~3 套 build，出击时选预设。存储格式
就是 `WeaponBuild` 的 JSON，和协议里的压缩形式互转。

## 7. 协议与网络

### 7.1 配装包（C→S）

现在 `Msg.Loadout` 里是 `u8 attachment`。改为变长 build 段：

```
u8  kind = Msg.Loadout
u16 weaponId
u32 traits
u8  contract
u8  extras
u8  squad
u8  slotCount
重复 slotCount 次: u8 slotKey, u16 defId
```

`slotCount` 最多 5，总长 ≤ 6 + 8 + 1 + 15 = 30 字节。旧字段位置保持不动，
新段追加在末尾；`PROTOCOL_VERSION` 加一，旧客户端直接拒绝（现有策略）。

### 7.2 远端外观（S→C）

别人也要看见你的镜/消音器。两个方案：

- **A（首版）**：快照 flags 旁边加 1 字节 `attachmentMask`（每槽 2 bit，
  编码"该槽的视觉变体"，不是完整 defId）。客户端按 mask 换模型。
- **B（完整）**：独立的低频 `Msg.PlayerBuild`（玩家 id + build），只在加入/
  改枪时广播；客户端按 id 缓存。适合配件数量多、视觉组合复杂的阶段。

首版选 A：1 字节、无额外包、和现有快照编码习惯一致。等 `action`/`ammo` 这类
"视觉上分不出来"的槽位出现时再转 B。

### 7.3 声音事件

`ShotEvent` 现在带 `attachment`（u8）。改成直接带 `loudness`（u8，0..255
映射 0..2），客户端不再需要知道对方装了什么，只需要知道这一枪有多响。

### 7.4 服务端校验

- `defId` 必须存在、槽位正确、接口兼容、没有冲突；
- 未解锁/未拥有的配件在首版直接忽略（不踢人，回落到空槽）；
- 每次 build 变化都重算有效属性并缓存，不要每次开火现算。

## 8. 客户端表现

### 8.1 通用挂点

在 `weapon-models.ts` 里给每把枪定义命名挂点（`Group`）：

```ts
interface WeaponMounts {
  sight?: Object3D
  muzzle?: Object3D
  magazine?: Object3D
  stock?: Object3D
}
```

配件模型只负责"以原点为安装面"建模，装配时直接挂到对应挂点，不再为每把枪
写一套位置。**机瞄的 SIGHT_Y / SIGHT_REAR_Z 约束只对"机械瞄具"成立**；
光学镜用自己的 `adsZ/adsPitch`，继续走现有的 `solveAdsY` 或镜筒流程。

### 8.2 机瞄替换

- 装光学镜时隐藏机械瞄具（避免镜筒里看到照门），开镜走 `scoped` 分支；
- 装觇孔/半照门时替换 `buildRifle` 里的后照门几何，**必须保持上沿对齐规则**
  （见 `docs/穿透与机瞄.md`）；
- 每换一种瞄具都要重新验证：相机/弹道线是否仍落在准星上沿。

### 8.3 性能

配件几何按 `weaponId + buildHash` 缓存：同一套 build 只建一次，切枪零分配。
不要为每个玩家单独建模型（远端玩家用 mask 选一套共享几何）。

## 9. 服务端实现要点

- `LoadoutState` 增加 `build: WeaponBuild`；`attachment` 字段保留为兼容别名，
  读的时候映射到 `build.slots.sight` 之类的旧语义，写完一个版本后删除。
- `heldWeapon()` 返回的是"基础规格"；新增 `effectiveWeapon(state)` 返回按
  build 计算后的只读视图。**所有判定只读 effective**，不要散落乘法。
- `magazineCap` / `canReload` / `canFire` / `switchTicks` 等 shared 函数改成
  接收 effective stats（或 LoadoutState 内部带缓存）。
- 断线重连：`resumePlayer` 已经保留整个 `LoadoutState`，build 自动跟着回来；
  Welcome 之后客户端会重发 Loadout，服务端按"已开过枪则忽略"的现有规则处理，
  所以 build 不会在重连时被意外重置。
- 局内拾取（第二阶段）：per-player 的 `foundAttachments` 只在服务端内存里，
  不进快照；通过 Loot 包或新的 Inventory 包低频同步。

## 10. 分阶段落地

| 阶段 | 内容 | 验收 |
|---|---|---|
| 0 | 隐藏旧系统（本次） | 菜单无配件入口；任何旧存档/旧包都不产生倍率、弹匣、外观效果；`pnpm test` 有守卫用例。 |
| 1 | 数据模型 + 兼容性 + 数值纯函数（shared） | 单测覆盖：接口不匹配拒绝、冲突拒绝、乘数上限、加法/乘法顺序、同 build 结果确定性。 |
| 2 | 配装协议 + 服务端生效 + 客户端预测 | 装 2× 镜后 `adsZoom` 变、装消音器后声音传播变、装长弹仓后弹匣变；两端判定一致。 |
| 3 | 工作台 UI + 视觉挂点（sight / muzzle） | 能装/卸、能看见模型变化、属性预览正确；重连后配装与外观不变。 |
| 4 | 局内拾取 + 死亡掉落 + 撤离结算 | 拾取的配件只在局内可用；死亡后出现在尸体缓存；撤离结算列出带出的配件。 |
| 5 | 仓库 / 商人等级 / 预设 | 需要服务端存档；单独评估，不与 1~4 绑在一起。 |

**建议首版范围（MVP）**：第 1~3 阶段 + 3 个槽位（sight / muzzle / magazine）
+ 6~8 件配件，只支持步枪与卡宾；霰弹/转轮在第二阶段补。不做耐久、卡壳、
归零、弹药类型。

## 11. 风险与需要拍板的决策

| 风险 | 说明 | 建议 |
|---|---|---|
| 数值爆炸 | 槽位一多，乘数叠乘很容易失控 | 先 3 槽 + 硬上限 + 每件都有负收益；新槽位必须先证明不会破坏 TTK。 |
| 视觉组合爆炸 | 5 槽 × 每槽 4 件 = 上千种外观 | 首版只做 sight/muzzle 的视觉，其余槽位用"数值 + 文字"先上。 |
| 持久化仓库 | 需要账号与服务端存档，当前匿名开发模式不支持 | 不要和配件一起做；先用金币永久解锁。 |
| 旧协议/旧存档 | 玩家本地存着 `dk.attachment` | 已用 `clampAttachment` 统一回落；新协议上线时再迁移键名。 |
| 远端外观带宽 | 每玩家每槽 2 bit 已够首版 | 超过 4 个视觉变体/槽时再上独立 build 包。 |

## 12. 立刻可做的准备（不依赖新系统）

1. 把 `weapon-models.ts` 里现有的 `createScopeAttachment` /
   `createSuppressorAttachment` 改成"以挂点为原点"的独立模块，便于复用；
2. 把 `AttachmentSpec` 的四个乘数字段收敛到一个 `WeaponStats` 形状，先让
   旧的 4 件配件走新接口（仍然隐藏），这样第 1 阶段的纯函数可以直接拿它们
   做回归样本；
3. 在 `docs/穿透与机瞄.md` 的机瞄约束旁边补一条"任何瞄具替换都必须过
   SIGHT_Y 对齐测试"。

---

**一句话总结**：首版不做塔科夫的全部，只做"接口 + 多槽 + 取舍 + 服务端生效
+ 可看见的模型变化"；仓库、耐久、局内掉落实物化留到有服务端存档之后。
