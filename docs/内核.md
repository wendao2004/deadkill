# 引擎内核

这份文档说的是"两端共用的那一套运行规则"，不是玩法。
内核移植自 `Claude-of-Duty` 的 `src/core`（见对方的 `PORTING.md` 第 3 节），
但只搬了契约，没有搬它的 Three.js 场景、DOM 输入和 rAF 循环 —— 那些是宿主的事。

## 1. 内核里有什么

`shared/src/kernel/` 四个文件，都是纯逻辑，不碰 DOM、不碰 Three.js、不碰 Rapier：

| 文件 | 职责 | 关键约定 |
|---|---|---|
| `fixed-clock.ts` | 真实时间 → 固定步数 | `rawDt` 先夹在 `[0, maxFrameDt]`；一帧最多补 `maxSubsteps` 步，补不完就**丢掉积压**；`alpha` 给渲染插值用 |
| `registry.ts` | 子系统注册与依赖拓扑 | id 唯一、依赖必须已注册、循环依赖在启动时抛错；`with(method)` 缓存"实现了某方法的系统" |
| `events.ts` | 同步事件总线 | `on` 返回退订函数；派发前复制订阅集合；单个 handler 抛错只记日志 |
| `rng.ts` | 确定性随机（xoshiro128\*\*） | `state()`/`restore()` 可存档；`forkFor(seed, label)` 按 (种子,标签) 哈希派生独立流 |
| `kernel.ts` | 帧相位编排 | `fixedUpdate × N → update → lateUpdate → render`；生命周期按拓扑序 init、逆序 dispose |

## 2. 两端的相位不一样，但规则是同一份

**客户端**（`client/src/game.ts`，用整套 `Kernel`）：

```
fixedUpdate  prediction     本地预测一个 tick（一个 tick 一条输入）
update       replication    远端插值采样（固定落后 INTERP_DELAY_MS）
update       presentation   相机/动画/HUD 采样
lateUpdate   feedback       命中标记、击杀播报、粒子收尾
resize       viewport       画布尺寸
```

**服务端**（`server/src/world.ts`，只用 `SystemRegistry` + `FixedClock`）：
服务端没有"画一帧"，所以不套 `Kernel` 的帧外壳，但一个 tick 内的顺序同样是
注册表算出来的，不是书写顺序：

```
lifecycle → monsters → inputs → physics → interactions → history → match → objective → broadcast
```

顺序本身就是玩法契约：怪必须在玩家输入之前动（否则射线永远差一 tick）、物理
只能在所有角色提交完 next kinematic translation 之后 step 一次、搜索/包扎必须
用物理推进后的落点、快照必须在目标状态机推进之后。`tests/phases.test.ts` 把
这个顺序钉死了，改顺序必须先改测试。

## 3. 新增一个系统

客户端：

```ts
kernel.add('mySystem', {
  init: () => { /* 建立资源 */ },
  fixedUpdate: (dt) => { /* 确定性玩法 */ },
  update: (dt) => { /* 表现 */ },
  dispose: () => { /* 释放 GPU 资源 */ },
}, ['presentation'])   // 依赖谁就先写谁
```

服务端：在 `World` 构造函数里 `this.phases.add(...)`，`deps` 写清前置阶段；
只要 `fixedUpdate`，因为服务端每 tick 只跑这一种相位。

两条硬规则：

1. **`fixedUpdate` 里的东西必须只依赖 `dt` 与共享常量**，不能读 `performance.now()`、
   不能读帧率、不能用 `Math.random`（要用 `forkFor(seed, label)`）。
2. **`update` 里不能改玩法状态**。表现层读、不写；写了就等于"帧率越高跑得越快"。

## 4. 确定性

- 服务端玩法随机全部走 `World.stream`（内核 `Rng`），出生点单独一条 `spawnRng`。
  两条流互不消耗，加一个选点判断不会让刷怪顺序错位。
- 客户端表现随机走自己的 `Rng`（`?seed=` 可固定），与权威判定无关。
- 仍有两处墙钟：断线保留计时（`Date.now`）与 `pump` 的推进节奏（`performance.now`）。
  前者本来就是真实时间语义，后者只决定"跑几步"，不进入模拟结果。

## 5. 共享层的边界

`shared/src/` 里凡是能被两端复用的规则都搬了过来，服务端保留同名薄适配层
（避免一次性改爆两百多处调用）：

| 共享模块 | 内容 | 服务端适配 |
|---|---|---|
| `loot.ts` | 搜刮点掉什么（纯函数） | `world.ts` 再导出 `rollLoot` |
| `matchDriver.ts` | 线索/放逐/撤离状态机 | `server/src/match.ts` 变成再导出 |
| `lagcomp.ts` | 回滚到哪一 tick、历史帧里的胶囊位姿 | `rewindTickFor` / `rewindTargets` 薄封装 |
| `snapshotView.ts` | 快照投影与 ackSeq 贴取 | `broadcastSnapshot` 只负责取数与发送 |

**没有搬的东西**：射线命中求解（`tryFire`）。它和 Rapier 的 `Ray` / 碰撞体句柄绑在
一起，要抽成共享模块得先定义 `RaycastPort`，收益（客户端预览命中）远小于风险
（判定路径改错就是"打中了不算"）。要做的话，单独一次改动、带完整回归再动。
