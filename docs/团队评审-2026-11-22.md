## 0. 一句话结论

**DEAD KILL 的工程底座、菜单审美和“猎杀骨架”已经达到可演示水准；但它现在还不是一款“能约朋友反复玩”的猎杀游戏。**

四颗地基钉还没接上：

1. **撤离只认赏金携带者** —— 队友和其余玩家即使活着、满包战利品，也无法把东西带出去；
2. **成长与结算只在 localStorage** —— 改 F12 就能满天赋、满配件、自写金币；
3. **服务端世界准入没有上限** —— 任意 `?match=` 都能懒建 Rapier World，512MB 部署可被单用户打爆；
4. **大厅身份只信好友码** —— 公开好友码 + 客户端 `partyId` 可冒充入队/代操作。

再加上浓雾夜图白屏、远景树线纯黑切边、武器展示全黑，第一眼和第一局都还差一口气。

**综合评分：5.6 / 10（六角色等权；关卡为主控补评）**
**定档：L3（有系统）→ 正在补内容密度与验收覆盖；尚未达到可公开 PvP 的 L3+。**

## 3. 做对了什么（不要动的地基）

1. **服务端权威是真的。** 位置、命中、伤害、掉落、目标、Boss 与怪物 AI 都在 `server/src/world.ts`；`applyHit/kill` 是单一结算入口，客户端改前端只能骗自己的屏幕。
2. **双端同源。** `shared/sim.ts` + `character.ts` 被两端逐字共用；60Hz 固定步、手写二进制协议、版本不匹配硬拒。
3. **延迟补偿方向正确。** 解析 capsule 求交 + 32 帧历史，回滚上限已从固定
   250ms 收到 **120–150ms（按服务端实测 RTT）**，避开 Rapier AABB 回滚坑；有测试覆盖。
4. **断线重连有真实设计。** 按 `userId` 保留角色、旧 socket 接管、ackSeq/queue 清零，不是“断了就重开”。
5. **命中反馈链完整。** 粒子/贴花/光照脉冲/命中标记/方向弧/分层声音/顿帧；这不是占位。
6. **菜单与世界观层。** 印刷/错版/琥珀色的 1890 沼泽识别度很高；菜单是全场最像成品的一块。
7. **五张地图有身份。** 沼泽农舍、教堂墓园、采石场、火车站、松林营地，剪影与天气组合能区分。
8. **程序化音频层比接线完整。** HRTF、空气低通、声速延迟、混响、材质脚步、怪物步幅、Boss 音色都已实现；缺的是几个事件的空间化接线，不是从零做。
9. **QA 脊柱。** 固定 seed/dt/cam/shot、`__stats()`、场景哈希、截图/冒烟/基准/diff 工具齐全；306 条测试是真资产。
10. **性能达标（本轮实测）。** 1080p quality 档在 GTX 1660 SUPER 上锁 60fps，341 calls / 193k tris，预算内。
11. **失败隔离。** 内核按系统/阶段 try/catch，后处理链有自检与 ACES 回退，单系统崩溃不拖垮整帧。

## 4. P0：进入下一阶段前必须解决

> 截至 2026-11-22 晚，P0-1（个人撤离）、P0-2（服务端 profile）与部分 P1
> 已落地，见 §13；本节保留评审当时的判断，便于对照“为什么做”。P0-3/P0-4
> 仍留到 Week 2。

### P0-1 撤离只认赏金携带者：队友与其余玩家无法兑现

**证据：** `shared/src/matchDriver.ts:286-337` 的 `stepExtract` 只用 `carrier()` 推进；`shared/src/match.ts:188-194` 的 `isPersonalEscape` 只认 `bountyCarrier === playerId`；`client/src/main.ts:535` 金币只给 `escaped`；`client/src/overlay.ts:270-273` 非携带者统一显示“失败 · 这一趟什么也没带回来”。

**影响：** 双人局 A 带赏金撤离，B 即使活着、满包战利品也判失败、0 金币；16 人房只有 1 人兑现。搜刮、清剿、刀锋合同对其他人是空转；“带赏金撤离”变成“只有一个人能玩”。

**需要拍板：**

- **A. 保持现状**：只有携带者能撤。规则简单，但多人局的个人收益没有出口；不推荐。
- **B. 个人撤离（推荐）**：任何玩家在撤离点读满 20 秒都能带自己的 loot 撤离；携带赏金者额外结算赏金。携带者撤离仍可结束本局；非携带者撤离后离场/观战，不强制结束他人对局。

**工作：** 协议 + 服务端 + 结算 + 测试，M–L（约 3–5 人日）。
**验收：** 双客户端 A 带赏金、B 同时在撤离圈 → 两人都看到“撤离”并各自入账；B 不在圈内仍失败；非携带者单人撤离能保住 loot；倒地者不能撤离。

### P0-2 成长与结算只在 localStorage，服务端只 clamp 不校验

**证据：** `client/src/main.ts:101-131` 读写 `dk.coins` / `dk.traitOwned`；`client/src/main.ts:528-537` 客户端按 `(lootValue+bountyValue)/5` 算金币；`server/src/world.ts:1749-1758` 直接接受 Loadout；`shared/src/traits.ts:205-217` 只限等级/条数；`shared/src/weapon-build.ts:286-299` 只查槽位兼容；`server/src` 没有 profile/wallet 路由。

**影响：** 改 localStorage 就能带 Vigor III + Bulwark III + 4× 镜 + 消音器 + 免费补给进 PvP；服务端照单接受。清缓存/换设备进度归零；PvP 起跑线不一致；撤离结算刷新即丢。

**修法：** 用宿主 `userId` 建服务端 profile（coins / trait owned / attachment owned / 已付款 extras）；Loadout 只传“选中位”，服务端用 owned 重算并结算；localStorage 降级为显示缓存。
**工作：** L（约 5–8 人日）。
**验收：** 篡改 `dk.traitOwned` 后发配装，服务端实际 traits=0；清 localStorage 重进金币/天赋不丢；换浏览器同账号同余额；撤离结算服务端只发一次。

### P0-3 世界准入无全局上限：任意 `?match=` 可懒建世界

**证据：** `server/src/game.ts:433` 从查询参数取 `match`；`:615-617` 先 `registerLevel` 再 `registry.get(matchId) + addPlayer`；`server/src/worlds.ts:180-191` 的 `get()` 无条件 `new World().start()`；`worlds.ts:59/165-167` 的 64 房上限只被 `POST /api/rooms` 使用，WS 路径完全绕过；`server/src/world.ts:1584` 只限单房 16 人；`docs/接入 WebLearning.md:9-10` 写明 `--max-old-space-size=384` / 容器 512MB，每房 8–20MB。

**影响：** 一个已登录用户开 N 条 WS、每条不同 `match`，无需创建房间，即可建 N 个 60Hz Rapier 世界；10–20 条连接吃 80–400MB，超过 heap/容器，Node 崩溃会连带宿主 WebLearning 进程。空房还要 5 分钟才被扫。

**修法：** `WorldRegistry.admit()` + `MAX_ACTIVE_WORLDS`（512MB 下 1–2）、每账号/每 IP 的 WS 连接上限、RSS 水位保护；超限 4xxx 拒绝；`POST /api/rooms` 上限按同一内存预算下调。
**工作：** M（约 2–3 人日）。
**验收：** 512MB/384MB heap 容器中第 3 个不同 `match` 的 WS 收到明确拒绝；RSS 稳定在 300MB 以下；100 次握手/断开后 `worlds.size` 回到 0；测试覆盖“WS 绕过 POST /api/rooms”。

### P0-4 大厅身份即授权：公开好友码 + 客户端 partyId 可冒充

**证据：** `server/src/game.ts:97-105` 的 `GET /api/presence` 向任何人返回所有在线者 code/name/roomId；`game.ts:184-199` 的 `GET /api/party/state?code=` 不校验请求者，直接返回 partyId 与邀请；`game.ts:329-375` 的 leave/room/launch 只认 body 里的 code；`partyId` 由客户端 Loadout 携带（`shared/src/protocol.ts:215-234`、`server/src/world.ts:1782-1783`），服务端直接按它编队并共享出生点（`world.ts:1905-1930, 1963-1979`）。

**影响：** 攻击者从 presence 读到目标 code → 从 party/state 拿到 partyId → 连到同一房间并带同一 partyId：被编进同一队、共享出生点、互相无友伤；还可替对方接受/拒绝邀请、以队长身份 launch。双人组队是核心模式，队伍边界形同虚设。

**修法：** HTTP 侧复用宿主 `authenticate`，所有 presence/party 路由以 session userId 为身份，不信任 body/query code；party 成员表由服务端维护；Loadout 的 partyId 只作为申请并与服务端记录比对；`GET party/state` 仅对成员返回 partyId。
**工作：** M（约 2–3 人日）。
**验收：** 冒用 presence code、越权读取 party/state、注入 partyId 三条路径均被拒；生产环境即使登录也成立。

## 6. P2：打磨与内容

- **PvE 击杀没有即时回报**：普通怪只给合同进度/回血，不给现金/物品；玩家会学会绕开。建议怪尸可搜或击杀 $10–20。
- **每局线索/血巢/撤离点/事件时刻固定**：第 3–4 局开始背路线；建议 3 选 2 线索、3 选 2 撤离、事件时间抖动。
- **合同按钮只有名称**：目标/奖励藏在 `title` 悬浮提示；建议常驻显示目标 + $奖励。
- **室内声学未接线**：`setAmbienceBias('indoor')` 从未在局内调用；远端搜刮/包扎无方位声；建议补。
- **怪物没有视锥**：360° 距离感知，背后接近仍会锁定；消音/潜行叙事打折。
- **经济边界**：击杀 $50 可互刷；刀锋合同可倒地补刀；持刀搜弹药会丢失；赏金 500 只在客户端计算。
- **文档漂移**：README 曾写协议 24/测试 264（本轮已改为 25/306，并补团队与评审文档索引）；`docs/architecture.md` 的协议行已同步；自动画质描述、体积雾步数、动态分辨率秒数仍待对齐。
- **开发体验**：`node --watch src/index.ts` 会监听 `node_modules`，启动时反复重启；建议 `--watch-path=src --watch-path=../shared/src`。
- **截图尺寸**：请求 1600×900，实际 1584×749（窗口边框）；建议 `Emulation.setDeviceMetricsOverride` 钉视口，并写同名 JSON 元数据。
- **昼间萤火虫 / 水面亮纹**：白天仍有黄色光点；水面 crest 在泥地上读成发光拖痕；建议按昼夜/材质衰减。
- **写实分支不可达却仍加载 8.7MB PBR 贴图**：`render.ts:724` `realistic=false`，但每局 `loadTextures()` 仍加载 12 张 1024² JPEG；手绘档不使用。建议手绘模式跳过，或改成显式 debug 开关。
- **水面不随时间/天气变化**：`props.ts:565-583` 只在构造时取雾色；`setModifier/setDaylight` 不更新 water；夜里水带偏亮、浓雾里水面偏清楚。
- **雨溅射 additive 发光圈**：`rain.ts:132-140,205` 固定颜色 + AdditiveBlending，夜间成亮圈、白天像作物圈；建议 NormalBlending 或乘场景亮度。
- **远端换弹/怪物嚎叫无遮挡**：`game.ts:1242-1248` 换弹、`:2277-2280` 嚎叫不传 `heardThrough`；墙后仍像在房间里。建议统一走 open() 遮挡链。
- **第一人称武器/手近景弱**：`review-weapon.png` 黑底无接地，枪托融入背景，手读成木块；建议展示机位 + 轮廓光 + 地台，play 机位抬亮 0.3–0.5 档。

## 7. 美术与关卡

### 7.1 美术与音频：继续手绘，冻结写实

**方向裁决：继续手绘伪 3D，冻结写实 PBR 分支。**

理由：

- `render.ts:724` 的 `realistic` 被硬编码为 `false`，没有 URL/设置入口；写实分支当前不可达。
- 真正转写实需要 `docs/写实风开发计划.md` 里 25–40 人周的外部资产（UV、贴图、骨骼、动画），远超当前产能。
- 手绘档的信息量来自轮廓、色阶、排线；低模 + PBR 光照会“一眼假”，这正是截图里局内平的原因。
- 写实分支仍让每局加载 8.7MB PBR 贴图（12 张 1024² JPEG），手绘档不使用；这是白白付出的下载/解码/VRAM 成本，也让所有修复要做两遍。

**三条基础管线互相打架（先修这三条）：**

1. **夜间浓雾比白昼更亮。** `review-quarry-night.png` 全图 mean=114.2、p50=114、p95=159，几乎没有暗部；`review-pine-day.png` mean=104.9、p50=88。夜间浓雾 `fogTint=0x9aa08c`（`modifiers.ts:56-67`）被直接用于天空 horizon/mid 与体积雾 in-scatter（`atmosphere.ts:870-894`、`postfx.ts:393`），`setDaylight` 只切光不切雾色。结果 19:00 读成阴天白雾，“先看见的人赢一半”失效。
2. **天空远景林线是一条纯黑横带。** `atmosphere.ts:337-342` 从 h=-0.30 填到 ridge≈0.01–0.04，`uTrees=zenith×0.46`（近黑），且天空材质 `fog:false`，不随雾/天气/昼夜变色。五图全天候可见，像世界尽头的黑墙。
3. **道具墨线被全局关闭。** `props.ts:443-447` 的 `makeInkMaterial` 末尾无条件 `mat.visible=false`；枯树、栅栏、墓碑、搜刮点全部走它。关卡盒刷仍有描边，道具没有，手绘母题在道具层整体消失。

**音频：实现比接线完整。** HRTF 25m、空气低通、声速延迟、混响、材质脚步、怪物步幅、Boss 音色都有；但：

- `BossPulse` 拿到事件坐标却只传 `bossKind`（`game.ts:1639-1643`、`audio.ts:1958-1960`），砸地/钟声永远贴耳满音量、无方向；
- 远端换弹与怪物嚎叫不传 `heardThrough`（`game.ts:1242-1248, 2277-2280`），墙后仍像在房间里；
- 室内声学 `setAmbienceBias('indoor')` 从未在局内调用；远端搜刮/包扎仍无方位声。

**验收：** 同机位 07:00/19:00 × 浓雾/死寂各一张：night mean < day mean，night p95 ≤130，40m dummy hunter 与背景灰度差 ≥25；天空无连续纯黑带；枯树/栅栏/墓碑外轮廓 2–3px；`review-weapon` 3/4 侧机位能逐一指出枪托/机匣/护木/双手，p99≥120；Boss 20m/60m/隔墙三档可听出方向与远近。

| 地图 | 盒刷 | 线索 | 撤离 | 搜刮点 | 巢穴 | 出生点 | 线索离散半径 | 撤离点距线索质心 |

**诊断：**

- **五图身份成立。** 沼泽农舍是最大、最分散的一张（1610 盒刷、线索离散 120m）；教堂/采石场更紧凑（49–55m），遭遇更快；车站有月台/轨道的高差；松林是雾与林线的潜行图。这个差异值得保留。

**建议（与主策 P2 合并）：**

1. 每局 3 选 2 线索、3 选 2 撤离，血巢随抽取线索质心移动；事件时间在窗口内抖动。

## 22. 第二轮画面打磨：中景可读性、地面材质、植被（2026-11-24）

**1. 中景被雾吃掉（40–60m 建筑洗成土黄块）**

## 23. 第三轮画面打磨：屋顶、立面构件、枯树与石墙（2026-11-24）

这一轮仍然先在 GTX 1660 SUPER 上按固定机位实拍，再对着截图逐项修。
和前两轮不同的是，**这次的证据链修了一个方法论错误**：同一个 `?match=` 复用的
World 会在几分钟后换天气，前后两张截图因此可能一张是黎明、一张是深夜，"改前改后"
根本不可比。现在每个机位用一个全新的 match 号（`fx-12` / `fx-19` / … 都是白昼
07:00），侧车 JSON 里的 `modifier` / `modifierHour` 必须一致才算 A/B。

**1. 每一栋房子的屋顶都浮在墙上方 0.4–1.6m**

`SHELLS` 表里手写的 `top` 与地图实际墙高**七栋全部不一致**（谷仓写 7.6、墙是
6.0；磨坊主屋写 3.8、墙是 3.2）。实测办法：墙体是长条盒、屋顶坡板/家具是短盒，
按"每个高度上累计的墙面长度"投票，得票最高的那个高度就是墙顶；顺带取这些盒子的
x/z 范围就是墙体的真实外轮廓。屋顶现在压在这个量出来的高度上，檐板/角柱/踢脚
也贴着真实轮廓放，不再按手写表猜。

**2. 立面没有交接线**

纯色盒子缺的不是细节，是**交接线**：墙和屋顶怎么接、墙角和墙面怎么分、墙和地
怎么站住。新增一层合并几何（每栋 12 个盒子 → 2 次绘制）：

- 檐板一圈（墙顶，外凸 0.05m）—— 屋顶"坐"在墙上的硬阴影线；
- 四根角柱（0.24m 见方，地面到檐板）—— 包住盒子最硬的四条竖棱；
- 石砌踢脚（0.34m，外凸 0.05m）—— 墙不再直接插进地面。

三个构件都不跨门窗洞口，所以不需要知道洞口位置，也就不会出现"钉在窗户上的横梁"。

**3. 屋顶和墙一个颜色**

关卡里的坡屋顶是 `wood` 盒刷，正午顶面朝天、受光最强，配上和墙相同的木色，
40m 外整栋建筑就塌成一个土黄方块。`comicWoodSurface` 本来就有"朝上的高木面 →
瓦片"分支，只是只换了图案没换明度。现在这个分支末尾乘 `vec3(0.58, 0.62, 0.70)`：
屋顶比墙暗一档半、且偏冷。石板瓦色 `VILLAGE_COLORS.roof` 同步压到 `0x3d4249`。

**4. 枯树：三处独立的错**

- **枝条分叉浮在半空**：主枝经 `rotateZ(π/2+droop)` 后是朝 −X 伸展，经
  `rotateY(−ang)` 后轴线是 `(−cos·cosAng, −sin, −cos·sinAng)`。旧代码只按 +X
  偏移侧枝，于是每根侧枝都悬在树干另一侧的空气里 —— 中景就是"一堆绕着树飘的木棍"。
- **枝条比树干还像横担**：`len` 给到 4m、`droop` 只有 0.06–0.22 rad，配上 7m 树干
  就是电线杆挂横担。改成越往上越短（0.95→0.48 倍）、下垂 0.34–0.80 rad、11 根。
- **树干是光滑纸筒**：9 边等径圆柱径向抖 5cm，断顶从"0.075→0.22 的小圆锥"换成
  粗残桩 + 两根劈裂木刺。另外枯树资产标签是 `['tree','dead']`，之前被归到
  `foliage` 表面 —— 树皮上印着叶簇斑块。现在 `dead` 走 `wood`。

**5. 程序化枯树和 GLB 枯树并排站着**

`loadNature()` 在 `generatedTrees` 为真时直接 `return`，永远走不到
`setNatureVisible(false)`，于是 props 里那 5 棵"光滑圆锥"枯树一直和
`pine_dead.glb` 并排。现在 props 把枯树与树挂单独放进 `procedural-dead-trees`
组，生成资产接管时只藏这一层 —— **芦苇不能跟着砍**，它是沼泽唯一的环境标志。

**6. 墙根的"荧光绿小棍"**

那是程序化芦苇，落位条件写反了：
`if (wetness < 0.08 && rng() > 0.2) continue` —— 旱地芦苇有 80% 概率被**保留**。
谷仓正面一排四五根就是它。改成 `< 0.15 && rng() > 0.06`。同时把一丛 3 片叶
（中景收成一根竖线）改成 6 片叶、根部外推 6cm，仍是 18 个三角形。

**7. 石墙像印刷的砖纹壁纸**

护堤是玩家几乎每条视线都会看到的东西，而原来的砌法是完全规则的顺砌：固定
0.78×0.30、隔行错半块、6mm 等宽灰缝。三处便宜的打破：砌层沿 X 缓慢下沉
（±9cm 噪声）、每行错缝量改成按行随机、每块石头的缝宽单独哈希。灰缝对比
0.42 → 0.30，砖面亮度按 3×3 区块共享（成片风化，不是逐块彩纸屑）。

**证据（GTX 1660 SUPER，1600×900）：**

- `.qa-shots/polish/facade-a.png`（屋顶浮空 + 墙顶亮线）→ `final-b.png`
- `.qa-shots/polish/tree-c.png`（浮空分叉）→ `tree-h.png`（只剩一棵 GLB 枯树）
- `.qa-shots/polish/probe-reed-magenta.png`（品红定位出的芦苇）
- `.qa-shots/polish/roof-c.png`（屋顶与墙同色）→ `roof-d.png`

  p99 **16.8ms**、**hitches 0**
- `pnpm test` **348/348**；`qa:smoke` 7 步通过、`__errors=0`、测试后 Chrome 进程 0

**仍未解决：**

- 关卡自带的坡屋顶盒刷仍被 GLB 屋顶包在里面（GLB 屋顶现在大多不可见），
  这是浪费，但改它要动关卡碰撞体，不在本轮范围。
- 建筑立面还是"墙板 + 檐板 + 角柱"，缺门廊、雨棚、招牌这类**大尺度**构件。

## 24. 第四轮画面打磨：门、檐下封板与阳台误用（2026-11-24）

上一轮把"屋顶浮空、立面缺构件"补到了"墙板 + 檐板 + 角柱"。这一轮拿 **7 栋房子
逐一近距离实拍**，先看"哪一块最像没做完"，再动代码。结论是门口。

**1. 门口是一个亮着的方洞**

近距离看，主屋的门洞里有 2 条亮横线、4 个亮格 —— 一开始以为门框 GLB 里方格里
是玻璃。查 `DoorFrame_Flat_WoodDark.gltf` 只有 108 个顶点、单 mesh，是一圈**空框**；
亮格子是从洞口看进屋里，而屋里被半球环境光整个照亮（toon 不遮挡），所以门洞就是
一块发亮的墙。7 栋房子全部如此。

补的门是"五块竖板 + 一块背板 + 两道铁门带"：

- 板缝 1.4cm。第一版给了 3.5cm，缝里直接透出屋内白墙 —— 一扇门像装了一圈灯带。
  背板（`parts.trim`）是必须的，它把缝变成暗线，不再是光源。
- 门扇落在 `uz = -0.2`：门框 GLB 比墙面内凹 0.15–0.25m，门扇贴洞口平面会盖住门框。
- 铁带用 `metal` 材质，给门一条尺度和材质对比（木色门板在阴影里是一整块糊）。
- 门楣 + 两根门柱 + 石础 + 门槛石构成门套。门柱只外凸 2cm、宽 24cm：更凸就从
  "门框"变成"立在门口的两根柱子"。

**2. 门朝哪：不读手写角度，读墙**

新增 `doorBasis()`：按"门离哪一面墙最近"判定外法线，再给出局部坐标（`ux` 沿墙、
`uz` 朝外）。之前 `door.rotY` 只描述门框模型自己怎么转，跟"门开在房子哪一侧"是
两件事 —— 混用之后任何需要朝向的构件都只能猜。现在 7 扇门共用一套 `pushOriented()`，
写坐标不用关心这栋房子朝南还是朝西。

**3. 阳台被当成栏杆摆在门口**

`SHELLS['marsh-p0'][0]` 挂着一个 `Balcony_Simple_Straight`，`place()` 的 y 是地面，
于是 1.2m 高的阳台变成一道横在门口的栏杆，正对着门，把人挡在外面。这排房子只有
一层，阳台没有地方放，删掉。

**4. 屋檐：锯齿瓦口 + 翻出来的瓦当背面**

从侧面看，屋顶檐口是一条锯齿状花边（圆瓦瓦口一高一低，非等比缩放后放大成闪电），
下面是出檐底面直接露出**一排瓦片的背面**（一排石砌色块）。两层都要补：

- `buildEaveFascia()`：沿**屋顶自己的**轮廓走一圈 30cm 封檐板，把瓦口盖住。
- 同一函数里再加一块**檐下封板**（`roofBase - 0.03`，厚 8cm），把出檐底面封成
  深色木板。这是屋顶从下往上看最容易穿帮的一处。

顺带把檐板从 22cm × 22cm 收到 12cm × 16cm：新封檐板顶上之后，两道 22cm 的平行
横带在一米外读成"刷了两道黑漆"。

**5. 雨棚只给"墙够高"的房子**

小房子墙顶 3.2m、门高 2.5m，门头上只剩 0.7m，塞不下雨棚。`PORCH_MIN_CLEARANCE
= 1.05` 把雨棚限制在谷仓（墙顶 4.8m）与磨坊（6.0m）两栋。

斜撑第一版手填"长度 + 倾角 + 中心高度"三个量，三者互相打架，上端离棚底差 15cm，
截图里是两根悬空的木棍。改成给两个端点（贴墙点、顶进棚底的点），长度与倾角自己算，
上端故意多顶进 5cm 藏在棚板里。

**6. 芦苇不再发荧光绿**

`props.ts` 的逐丛色相 `HSL(0.22, 0.42–0.62, 0.36–0.50)` 在直射光下是一片荧光绿，
灰色泥地上像塑料草。压到 `HSL(0.20, 0.32–0.48, 0.30–0.42)`，读成发黄的浊绿。

**方法论：品红定位**

这一轮有两处"看到的和我以为的不是同一个东西"：门洞里的亮格子、屋檐下的石砌色块。
两次都是把材质临时染成 `0xff00ff` 再拍一张 —— 品红的才是自己加的构件，剩下的
（关卡墙体、屋顶盒刷）立刻排除。比读几何代码快一个数量级。

- `.qa-shots/polish/probe-trim.png`（品红标出檐板/角柱/门套）
- `.qa-shots/polish/d6-church.png`、`d6-station.png`、`d6-quarry.png`（其余建筑落位复核）
- `docs/perf/polish5-marsh-quality-1080.json`：avg **16.67ms**、median 16.7、
  p99 **16.8ms**、**hitches 0**
- `pnpm test` **348/348**；`qa:smoke` 7 步通过、`__errors=0`、测试后 Chrome 进程 0

## 25. 第五轮打磨：开着的门、板条墙、室内不再是天空（2026-11-24）

第四轮把门装上了，问题也正好出在"装上了"：门洞在关卡碰撞里是**通的**（2.4m 宽、
整高 3.2m、没有碰撞体），而门扇关在洞口上 —— 玩家能直接穿过去一扇看着关着的门。
看到的和能做的对不上，比没有门更假。

**1. 门扇摆开门内**

`pushSwung()` 把整扇门（五块竖板 + 背板 + 两道铁带）绕一侧铰链摆进屋里 100°。
门洞保持通畅，玩家的判断（"这扇门开着，能进"）和碰撞一致，顺带把屋内的暗部露出来。
铁带必须跟着门扇一起摆 —— 门开了铁带还钉在洞口平面上，是最容易被看穿的一种。

**2. 门套 2.4m 高：门柱要有石础**

一层房子的门高达 2.5m，两根 3.4m 的细木柱如果没有基座，读成"立在门口的两块板"。
门柱加宽到 24cm、下端补 36cm 石础，与门楣咬合成门套。

**3. 13m 长的立面只有竖细线**

木板墙原来是 42cm 一道 1cm 缝、对称、无明暗。远看是一块米色平板刷了几条细线 ——
看起来像一个集装箱。改成**板宽 30cm + 压条**：每条板缝上盖 6cm 压条，压条两侧
各压一道暗沟（`groove`），板面本身给 14% 的横向明度渐变。明度断层才是眼睛读作
"凹凸"的东西，几何仍然是一个面片。再加墙脚 55cm 的溅泥，木板不再直接插进地面。

**4. 披檐底面是一条发白的亮带**

`buildPorch` 的棚顶是 `parts.roof`，石板瓦材质朝下的那一面在天空色环境光下是一条
浅灰亮带，从正面看像"棚子底下插了一张卡纸"。补一块**深色底板**（`parts.trim`
里单独一块，几乎贴住棚板下沿），底面立刻收进阴影。

**5. 室内和外景一样亮：按"净空盒子"压暗**

toon 光照不做遮挡，屋檐下、屋里、墙洞里拿到的环境光跟露天一样多，所以从一扇开着
的门望进去是一间被天光灌满的空房。`interiorVolumes()` 从每栋房子的墙段里量出
**净空**（不是手写，见下），交给 `setInkInteriors()`；片元落在某个净空盒子里就乘
一个 0.21–0.31 的冷色系数。切换发生在墙的两面之间，正是物理上该发生的位置。

净空是 `measureWalls()` 顺手量的：只认贴轮廓外侧 0.35m 那一圈墙段，取它们的内侧面
—— 墙厚写死 0.4 就等着下一张图对不上。

**踩到的第一个坑：边界判据正好落在墙内表面上。** shader 里是"严格在盒子里"（`m < 0`），
墙内表面的片元 `m` 恰好等于 0，于是每一面墙连地板一起全被判成"在外面"，量出来的
体积一点用都没有。修法是把盒子往外胀 6cm（墙厚 40cm，外表面还在外面 34cm），
地板从 `y0 - 0.12` 兜住。

**踩到的第二个坑（方法论）：同一个 `?match=` 会换天气。** 这一轮前后做过五六次
"改前 / 改后"的亮度对比，读数差几十级，一度以为室内压暗根本没生效。实际上两次
截图的 `modifier` 不同（4 和 7 都是 07:00，雾不一样），**跨截图比较亮度在这种
天气随机的地图上是无效的**。可用的办法只有两个：

- 同帧内比较（外墙 vs 门洞内的后墙，一张图里读两个区域）；
- 或者把判据结果直接染成品红拍一张 —— 品红覆盖 19.5% 像素、且透窗看到的外景
  塔楼不是品红，一眼就证明判据和边界都对。

以后所有"亮度/对比有没有变"的判断都走这两条，不再跨截图比。

## 26. 第六轮打磨：近地地面、加性细节与石作压暗（2026-11-24）

这一轮从"贴地视角"起手：把相机压到 0.85m、对着墙脚拍。近地地面占画面一半以上，
而它是一整片没有任何信息的深色 —— 前几轮修的地面都在 0–10m 之外才有内容。

**1. 为什么地面上的细节全都看不见**

`comicMudSurface()` 本来有裂缝、砾石、砂粒三层。问题不在有没有，而在**乘性**：
`outgoingLight *= tint`。近地地面大多落在建筑阴影里，`outgoingLight ≈ 0.04`（线性），
对它做 20% 的乘性调制是 0.032–0.048，换成 sRGB 只差 **1 个 8 位级**；再叠上 4 级
toon 压缩和抖动颗粒，等于没有。

**结论**：暗部的细节必须走**加性**通道。

新增 `comicSurfAdd`（GLSL 文件级 vec3，材质函数往里加，注入端在乘完之后加）：

```glsl
outgoingLight *= mix(vec3(1.0), comicSurf, comicDetail);
float comicGate = smoothstep(0.006, 0.045, dot(outgoingLight, vec3(0.2126, 0.7152, 0.0722)));
outgoingLight += comicSurfAdd * comicGate * comicDetail;
```

门限那一项是必须的：无门限的加性项在夜里会把地面抬成一张发光的板。门限卡在
0.006–0.045 这段正好是"阴影带"，夜里的地面（<0.02）几乎不抬。19:00 实拍复核
（`.qa-shots/polish/q7-night.png`）：地面没有白点、没有发光。

泥地的加性项是三样**会反光的东西**，不是三样更深的颜色：干裂板的翘边（`crust`）、
枯草（`straw`，17cm × 59cm 的格子 + 细长遮罩，读作"躺着的草茎"而不是方块）、
散落的亮砂（`pebble`，圆形 + 抖动）。

**2. 两次做过头，都靠实拍抓回来**

- **第一次：满屏方形彩纸。** 最先写成 `step(0.972, comicHash21(floor(p * 31.0)))` ——
  3cm 轴对齐格子里的硬门槛，于是每几个像素就有一个正方形亮块，地面像撒了数字噪声。
  改成"每 11cm 格挑一个候选 + 格内径向遮罩 + 格心抖动 + 尺寸随机"才是圆石子。
- **第二次：整个广场变成瓷砖。** 泥板原来是 1.05m × 0.83m 的格子，加 0.055 的亮边
  之后，**广场上出现一整片规则的浅色网格** —— 正是上一轮好不容易去掉的"地板革"。
  三处一起改：板缩到 46cm × 37cm（真实的晒裂泥本来就是手掌大小），两级 warp
  （0.90 + 0.38），裂缝与翘边乘一个低频遮罩 `crackMask`，让一半地面有裂缝、一半被
  踩平。规则性被打散之后，同样的强度才读作"干泥"而不是"砖"。

**3. 石砌踢脚比木墙还亮**

`VILLAGE_COLORS.stone = 0x6a675f`，在 07:00 的冷环境光下是一条发亮的蓝灰带，
挂在每栋房子底部，读成"贴在墙上的踢脚线"。压到 `0x5b564c`，并给竖面的石作补
墙脚 55cm 的溅泥（与木墙同一条规则）。石材从此落在木墙之下，符合"基座比墙暗"。

**方法上的一句话**：*亮的东西要加，暗的东西才能乘。* 这一轮所有"看不见的细节"
都出自同一条判断失误 —— 在 0.04 的亮度上做乘法。

**证据（GTX 1660 SUPER；白昼 `modifier 4` / 07:00，黄昏 `modifier 1` / 19:00）：**

- `.qa-shots/polish/q1-ground.png`（改动前：一片空白的地面）→ `q7-ground.png`

- `.qa-shots/polish/q5-door.png`（第二次做过头：广场瓷砖）→ `q6-door.png`

  p99 **16.8ms**、**hitches 0**

**仍未解决：**

- **远景（>40m）仍是灰盒。** 关卡盒刷建筑没有窗洞、没有门，只有一块米色立方体；
  盒子墙能靠程序化材质撑住，但"窗"这件事必须动几何或补暗面片。

## 27. 第七轮画面打磨：树干从"方木柱"换成锥形树皮柱（2026-11-24）

这一轮仍然先实拍。在沼泽村口蹲下看一眼就发现画面里最刺眼的东西不是房子也不是地面，
而是**一排 5–6m 高的巨型冰棍棒**：0.8m 见方、笔直、顶端一刀切平，表面贴的是木墙那套
"30cm 板条 + 6cm 压条"图案。近景像集装箱侧板，远景像插在地上的木牌。

**1. 根因：碰撞体一直在，装饰体被藏了**

关卡的树是 `BrushSet.tree()` 造的两块：0.8m 方柱（`wood`）+ 立方树冠（`foliage`）。
树冠会被棱球替换、GLB 松树接管后**整层隐藏**（`canopyMesh.visible = false`），
方柱却没有任何人去动 —— 于是每棵"已经换成 GLB 松树"的树底下都留着一根木柱。
农场那一区还有 8 根连树冠盒都没有的"界树"（`zone_farm.ts` 的 `stumps` 表，注释写着
"叶子由客户端装饰"，但客户端从来没补过）。

**2. 改法：认树干、换圆柱、补界树冠**

- `trunkBrushes(level)`：合批前认出树干。判据是"细长方柱 + 正上方 1.4m 内有树冠 +
  木料 + 高度 ≥ 3m"。**树桩（0.8m 高）留方**——树桩本来就该是一截矮方墩；
  灯杆/旗杆/篱笆桩是金属或石头的，也不动。
- `trunkGeometry()`：7 边、3 段、0.52 收分的锥形圆柱，沿角度做 ±12% 半径抖动
  （按盒子坐标取确定性种子，同一棵树每局一样），绕根歪 2°。整张图合并成**一份**
  `bark` 材质（`0x4b4238`，比木墙冷、暗一档半）。碰撞仍然是原来那 0.8m 盒子 ——
  树干在近景比 GLB 树干粗一点，但"粗一点的树根"和"方木柱"不是同一个量级的错。
- `scrubCrownGeometry()`：没有冠的界树补三层锥体。它们**不能**放进 `canopyMesh`
  （那一层会被隐藏），也不会有 GLB 树来接管（这些位置没有树冠盒刷），所以单独一份
  `foliage` 材质、永不隐藏。顶点色压到 0.82：GLB 松树的 VertexColor 是深橄榄绿，
  而关卡 `foliage` 的固有色是给盒刷准备的亮绿，不压就会在同一片林子里绿得发荧光。

**3. 三次做过头，三次靠实拍抓回**

- **第一版：只剩三片悬空的纸。** 锥体用了 `openEnded`。玩家站树下往上看，看到的正是
  锥体的**底面**，开口锥在这一视角下只剩一圈边缘 —— 三层叠起来就是三片三角形纸。
  改封口。
- **第二版：圣诞树插在电线杆上。** 冠只戴在柱顶 3m 内，15–30m 外是一排"棒棒糖"。
  针叶树的下部枝条本来就垂到接近地面：冠底压到离地 1.7m，冠顶只比柱顶高 0.9m。
- **第三版：叠起来的绿盘子。** 层高太扁时，每层锥体的底边是一条水平直线，读作
  "三只绿盘子"。把层高按 0.55 / 0.45 / 0.34 拉开（坡度接近 55°），并给最下一圈
  加 0.26m 的垂坠抖动 —— 底边一参差，"枝条末端"就出来了。

**4. 顺手修掉的一个方法论坑：`?match=` 会记住第一张地图**

同一 `?match=` 复用的房间，**关卡由第一个连上来的客户端决定**。先拍了
`?map=pine-camp-night&match=fx-303`，之后再拿 `fx-303` 拍沼泽，拿到的还是松林 ——
白拍一张。现在每个机位用全新的 `fx-N`；而 `fx-N` 的天气可以**离线算出来**
（`hashSeed` 是 FNV-1a，`modifier = rollModifier(new Rng(hashSeed(id)))`），
白昼 07:00 的号就近取 `fx-14/20/21/22/23`，不必一张张试。
