# DEAD KILL 开发团队

> 建立于 2026-11-22。这不是组织架构图，而是一套**可重复执行的评审与交付方式**：
> 六个常驻角色、统一的证据标准、固定的验收动作，以及明确的“现在不做什么”。

## 1. 团队使命

把 DEAD KILL 从“功能齐全、能跑通的原型”推到“能约朋友反复玩的猎杀游戏”。

判断标准只有一句：**玩家能不能在 15 分钟内走完一次有信息、有风险、有回报的猎杀，并想再开一局。**

所有取舍回到 `docs/direction.md` 的三根支柱：信息稀缺、一枪致命、声音即情报。
不服务这三句的系统，再酷也延后。

**人类负责人**保留最终取舍与发布决定。角色是评审视角，不是投票机器。

### 决策权

- 方向/砍功能：主策提出，人类负责人拍板。
- 数值/武器：战斗设计提出，技术总监确认服务端可实现，QA 确认有验收。
- 画面/声音：美术总监提出，性能预算由 QA 否决。
- 协议/数据/部署：技术总监提出，必须附迁移与回滚方案。
- 地图/点位：关卡设计提出，必须附坐标与审计数字。

## 3. 证据标准（硬规则）

1. **以代码与实测为准，文档可能落后。** README 的协议号、测试数、已知边界都要按当前代码校正。
2. 每条结论必须能落到：`文件:行`、测试名、截图路径，或可复现命令。
3. 区分置信度：`code-confirmed`（亲自读代码）/ `inferred`（推断）/ `needs-runtime`（需真机或双端）。
4. 禁止“看起来好了”。截图必须固定 `seed / dt / cam / q`，且 `__errors === 0`。
5. 不把旧评审已修项重新报一遍；先查 `docs/玩家视角评审-2026-10-29.md` §12 与当前代码。
6. 严重度：P0 = 核心循环断裂/首局劝退/可利用/丢数据；P1 = 明显伤害体验或系统失效；P2 = 打磨。

## 4. 固定验收动作

每次改动按影响选择最小集，但**发布前必须全绿**：

```bash
pnpm typecheck                          # 三包 0 error
pnpm test                               # 347 条（根 tests/ + client/tests/）
pnpm build                              # vite 生产构建
pnpm qa:smoke                           # 主界面→出击→暂停→回大厅→再出击
pnpm qa:bench -- --w 1920 --h 1080 --require-gpu \
  --url "...&bench=1&q=quality&seed=4207&noaudio=1&scale=1&dt=16.67"
pnpm qa:shot -- --out shot.png --url "...&shot=1&dt=0&cam=..."
```

QA 工具约定（2026-11-22 起）：

- 默认走**真实显卡**；`QA_GPU=0` 才回退 SwiftShader。`__stats().gpuName` 必须显示具体适配器。
- 测试结束必须清理 Chrome；工具按临时 `user-data-dir` 反查，Ctrl+C 也会清理。
- 截图/基准的预检超时 15 秒，避免 Vite 编译期间误报“服务不可用”。
- `qa-shot` / `qa-smoke` 断言 `gpuName`；`qa-bench --require-gpu` 在软件渲染时退出 3。
- `qa-bench` 支持 `--w/--h`，默认 URL 钉 `scale=1&dt=16.67`；avg 阈值含 0.5ms 采样容差。

## 5. 节奏与仪式

- **每周一 30 分钟：定优先级。** 主策 + 技术总监 + QA，只排本周能验收的 3–5 件事。
- **每周五 60 分钟：验收会。** 固定 seed 截图、冒烟、基准、`__errors`；不过就不算完成。
- **改协议 / 改地图几何 / 改经济结算**：必须触发一次跨角色评审（至少技术 + QA + 对应设计）。
- **每两周一次全面评审**：用六个角色并行跑，P0/P1 逐条对抗核查，再合并路线。
- **发布后 24 小时**：看断线、房间回收、错误日志与玩家反馈，补进下一周。

## 7. 现在不做什么（防止继续堆半成品）

1. 不在“浓雾白屏 / 黑色地平线 / 展示机位全黑”修好前加新地图或新天气。
2. 不在服务端 profile 落地前做跳蚤市场、赛季、保险等经济大系统。
3. 不在 1080p 基准与 CI 阈值建立前宣称“性能达标”。
4. 不在五张图的目标/搜刮/出生点审计归零前加第六张图。
5. 不用“以后会做”解释菜单里的假数据、假开关、假协议号。
6. 不为了写实分支继续投入 authored 资产，除非主策与美术总监共同证明它比手绘分支更能服务三根支柱。

## 8. 怎么用这套团队

在 Claude Code 中直接说“让主策评审最近的改动”“让 QA 跑一遍发布检查”，
或通过 Agent 工具选择 `dk-game-director` / `dk-combat-designer` / `dk-art-director` /
`dk-tech-director` / `dk-qa-lead` / `dk-level-designer`。

需要一次覆盖全部角色的评审时，用 Workflow 并行跑六个角色，再对 P0/P1 做独立对抗核查；
不要只让一个角色“顺便看看别的领域”——那会把专业判断稀释成泛泛而谈。
