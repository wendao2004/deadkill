# Dead Kill —— 技术栈决策

> 本文是**决策记录**，不是教程。每条结论都写了"为什么不选另一个"，
> 因为半年后回来看时，唯一有价值的就是那个"为什么"。

## 0. 目标与硬约束

参考《猎杀：对决》(Hunt: Showdown)：PvPvE 撤离射击，节奏慢、信息稀缺、
一枪致死、声音是核心情报。我们要做的是**硬核向**的 Web 端同类。

约束来自被复用的宿主项目 `D:\GithubProject\WebLearning`（Club_Space）：

| 约束 | 出处 | 对游戏的影响 |
|---|---|---|
| 单一 origin + Caddy 路径分流 | `deploy/Caddyfile` | 游戏前端必须是同源静态资源，不能单独起域名 |
| `connect-src 'self'` | Caddyfile 安全头 | **只能用同源 WebSocket**，不能连第三方信令/房间服务 |
| `script-src 'self'`，无 `unsafe-eval` | 同上 | 不能 eval 生成的着色器字符串（Three.js 用 WebGL 编译着色器不受影响，但 `new Function` 类方案全部出局） |
| 业务容器 2–4GB / 单容器 512MB | `deploy/docker-compose.yml` | 服务端不能常驻重型模拟；每房间 CPU 预算极小 |
| Node 24 原生跑 `.ts`（类型剥离） | `deploy/Dockerfile` CMD | 服务端**不引入构建步骤**，直接 `node src/index.ts` |
| SQLite (`node:sqlite`) 单进程 | `server/src/db.ts` | 存档/账号复用现有库，不新增数据库容器 |
| Fastify 5 | `server/package.json` | 游戏服务端作为插件挂到现有 app 上 |

## 1. 渲染：Three.js —— 选它，但要说清代价

**结论：Three.js r186 + 自写渲染管线。**

对比过的方案：

- **Babylon.js 9**：开箱的 PBR/后处理/导航网格更强，但整包 ~4MB(gz 1.2MB)，
  且它的 Inspector/GUI 会拉进额外依赖。猎杀类游戏要的是**自定义后处理**
  （胶片颗粒、色差、重体积雾、色调映射），这些在 Three 上用 EffectComposer
  几行就能拼，在 Babylon 上反而要绕开它自带的管线。
- **PlayCanvas**：引擎本身不错，但生态偏"可视化编辑器驱动"，代码优先的
  工作流要对抗它的资源系统。
- **Bevy / Unity WebGL / Godot Web**：WASM 体积起步 15–30MB，首屏在局域网
  NAS 上还行，但**调试体验**（无 source map、栈不可读）对"逐步实现"是硬伤。

**为什么 Three.js 仍然是对的选择**：它的体积可裁剪（只 import 用到的模块，
tree-shaking 后核心 ~150KB gz），着色器可控，而且我们是**代码优先**开发——
不需要编辑器。

**代价（必须承认）**：Three 没有内置的：
- 角色动画状态机 → 用 `AnimationMixer` + 自写状态机
- 网络同步 → 自己写（见 §3）
- 场景流式加载 → 自己做分块
- 地形/植被 GPU 实例化 LOD → 自己做（猎杀的沼泽芦苇必须做，否则帧数崩）

这些都是**已知工作量**，不是未知风险。

## 2. 物理：Rapier3D（WASM）—— 客户端与服务端同一套

**结论：`@dimforge/rapier3d-compat@0.21`，客户端与服务端共用。**

为什么不用别的：
- **cannon-es**：纯 JS，慢 3–5 倍，且没有角色控制器（character controller）。
  射击游戏最需要的就是胶囊体角色控制器 + 斜坡/台阶处理。
- **Ammo.js**：Bullet 的 Emscripten 移植，API 陈旧、包体大（~1.5MB）、
  维护停滞。
- **Jolt (jolt-physics)**：性能最好，但 JS 绑定成熟度和文档远不如 Rapier。

Rapier 的关键优势是 **`compat` 版本把 WASM 内联成 base64**，所以
- 服务端 `node src/index.ts` 直接能跑，不需要额外的 .wasm 文件搬运；
- 客户端 Vite 打包不用配 wasm 插件。

**服务端也用 Rapier 的理由**：命中判定必须服务端权威。如果用简化的
AABB 判定，客户端用 Rapier、服务端用 AABB，两边结果会不一致——
表现就是"我明明打中了却不算"。**同一套物理、同一份碰撞体**是唯一可靠的解。

**代价**：服务端每个房间一个 Rapier World，内存约 8–20MB，CPU 在
30Hz tick 下对 16 人房间约 3–6%。这在 512MB 容器里**只够跑 1–2 个房间**，
所以架构上必须做成"按需创建、空闲回收"（见 §5）。

## 3. 网络：原生 WebSocket + 自写协议，不用 Colyseus

**结论：`@fastify/websocket`（底层 ws）+ 二进制协议 + 自写快照/预测/和解。**

这是本文档最重要的决策，逐条对比：

### 3.1 为什么不用 Colyseus
Colyseus 提供房间管理、状态同步（`@colyseus/schema` 二进制增量）、
matchmaking。听起来正好，但：
- 它的状态同步是**全量状态 diff**，适合回合制/棋牌。射击游戏需要的是
  **每 tick 的位姿快照 + 客户端预测和解**，这是完全不同的模型；
  Colyseus 的 schema 帮不上，反而要绕开它。
- 它自带 HTTP 服务器和路由约定，与现有 Fastify app 集成要么让 Colyseus
  接管（破坏"入口只有一个"），要么跑两个进程（破坏内存预算）。
- 包体 ~200KB，且强耦合它的客户端 SDK。

### 3.2 为什么不用 geckos.io（UDP over WebRTC）
WebRTC DataChannel 的不可靠模式理论上比 WebSocket 更适合射击游戏。
**但在本项目的约束下不可行**：
- 需要额外的 UDP 端口映射；Caddy 当前只发布 TCP 端口，且
  `connect-src 'self'` 不覆盖 `stun:`/`turn:`。
- 局域网内没有 NAT 穿透问题，但 WebRTC 握手仍需 STUN server 配置，
  部署复杂度从"改一行 Caddyfile"变成"多一个信令服务"。
- Node 端 geckos.io 的维护活跃度低（最后版本 3.1.0，2022 年）。

**结论：先 WebSocket（TCP），在局域网 <5ms RTT 下完全够用。** 如果将来
要上公网/高丢包环境，再引入 WebTransport（HTTP/3）——Caddy 2.7+ 已支持
HTTP/3，这是比 WebRTC 更平滑的升级路径。这个判断写在这里，是为了
将来不用重新论证一遍。

### 3.3 为什么不用 SSE（宿主项目现有的实时层）
`server/src/realtime.ts` 明确写了"为什么用 SSE"：零依赖、单向推送够用、
EventSource 自带重连。**这些理由对聊天成立，对射击游戏全部不成立**：
- 射击是**双向高频**：客户端每 tick 上传输入（30–60/s），SSE 只能下行。
  用 POST 上传输入意味着每个输入一个 HTTP 请求，头部开销就是致命伤。
- SSE 走 HTTP/1.1 时浏览器有 **6 连接/域** 限制，且无法设置
  `binaryType`，二进制要走 base64（+33% 体积）。
- 延迟：SSE 没有背压控制，服务端 tick 推送会在代理缓冲区堆积。

所以游戏用 WebSocket，**与现有 SSE 并存**——聊天继续用 SSE，
游戏走 `/ws/game`。两者互不影响。

## 4. 协议：二进制，手写编解码

**结论：`ArrayBuffer` + `DataView`，手写读写器，不用 protobuf/flatbuffers。**

- 射击快照是**定长结构体数组**（每个玩家：id/位置/朝向/状态），
  protobuf 的 tag 开销在这里是纯浪费。手写定长 = 16 人快照约 300 字节。
- 不引入代码生成步骤 → 符合"服务端零构建"的约束。
- 代价：加字段要同时改两端。用 `PROTOCOL_VERSION` 常量 + 连接时握手校验
  来兜住，版本不一致直接拒绝（而不是静默解析错位）。

## 5. 服务端架构：房间即世界，按需创建

```
Fastify app (现有 server/src/index.ts)
  └─ registerGame(app)            ← 一个插件，不动现有路由
       ├─ GET  /api/game/status   ← 房间列表/健康
       └─ GET  /ws/game           ← WebSocket 升级
            └─ WorldRegistry
                 ├─ World(matchId)  ← 一个 Rapier World + 30Hz tick
                 └─ 空闲 5 分钟无玩家 → 销毁
```

**tick 循环不阻塞事件循环**：Rapier 的 `world.step()` 对 16 人房间约 0.3ms，
30Hz 下 CPU 占用 1%。**不需要 worker thread**——这与象棋 AI 不同
（那边一手棋 1.2s 同步递归，必须挪线程）。这个区别很重要：
不要因为"象棋用了 worker"就照搬，那会白白增加序列化开销。

## 6. 客户端架构：框架无关，可嵌入 Vue

**结论：纯 TypeScript + Vite，导出 `createGame(container)`。**

不直接写成 .vue 组件，理由：
- 游戏循环（`requestAnimationFrame`）与 Vue 的响应式系统是**敌对**的。
  把每帧 60 次的位姿更新塞进 reactive 会让 Vue 的依赖追踪成为瓶颈。
- 纯 TS 可以被任何宿主嵌入：现在的 WebLearning 桌面外壳、将来的独立页、
  甚至 Electron 壳。
- HUD 用**原生 DOM 覆盖层**而不是 Canvas 内绘制——DOM 排版文字更快更清晰，
  且能直接复用宿主项目的 CSS 变量/主题。

Vue 侧只需一个薄包装（见 `docs/接入 WebLearning.md`）。

## 7. 复用宿主后端的清单

| 能力 | 复用方式 |
|---|---|
| 登录/会话 | 复用 `auth.ts` 的 cookie 会话，`/ws/game` 握手时校验 |
| 账号/存档 | 复用 `node:sqlite`，新表 `dk_hunters` / `dk_matches` |
| 限流 | 复用 `ratelimit.ts` 的 `RATE_RULES`，加连接频率限制 |
| 审计 | 复用 `audit.ts`，记录对局开始/结算 |
| 静态资源 | 游戏构建产物放进 `web/dist/game/`，由现有静态服务托管 |
| 部署 | 同一个 app 容器，无新增容器 |

**不复用**：SSE 实时层（理由见 §3.3）、象棋的 worker 模型（理由见 §5）。

## 9. 分阶段实现路线

每一步都以"可玩"为验收标准，不做无法验证的抽象。

| 阶段 | 内容 | 验收 |
|---|---|---|
| **P0（本次）** | 骨架 + 网络 + 移动 + 命中判定 | 两人能互相打死，服务端拒绝作弊输入 |
| P1 | 地图：沼泽农舍（碰撞体 + 分块加载） | 有掩体的对战 |
| P2 | 武器系统：弹速/下坠/换弹/腰射与瞄准 | 射击手感与猎杀接近 |
| P3 | 音频情报层：脚步/枪声方位衰减 | 能靠声音定位 |
| P4 | PvE：怪物 + 声音引怪 | 打怪会招来玩家 |
| P5 | 撤离与赏金循环 | 一局完整流程 |
| P6 | 猎人养成/装备/永久死亡 | 局外循环 |
